## 1. 两分钟项目讲述：背下这个骨架

### 1.1 四段式

| 段落 | 时长 | 说什么 | 忌 |
| --- | --- | --- | --- |
| **背景/目标** | 20s | 这是什么、给谁用、要解决什么问题 | 别从"我学 STM32 开始"讲 |
| **方案** | 40s | 硬件选型 + 软件架构（画个框图最好） | 别逐个外设报菜名 |
| **难点** | 40s | 1~2 个真实问题 + 怎么定位 + 怎么取舍 | 别说"没遇到困难" |
| **结果** | 20s | 指标：响应时间、稳定性、精度 | 别只说"能跑" |

### 1.2 示例（可直接改成你自己的）

> 我做的是一个**环境监测小站**，用 STM32F103 采集温度，OLED 本地显示，串口上报给上位机，超阈值蜂鸣器报警。
>
> 硬件上，温度用 NTC 分压进 ADC，屏幕走 I2C，上位机走 UART。软件分三层：Hardware 放屏幕和传感器的驱动，App 层用状态机管页面、用 SysTick 做 1ms 时基轮询任务。
>
> 过程中遇到两个问题。第一个是屏幕和另一个 I2C 设备共用总线，单独测都正常，一起跑就偶发花屏。我判断是并发冲突，用逻辑分析仪看到一次传输中间插进了另一个起始信号，后来把所有 I2C 访问收口到一个任务、并用互斥量锁住整段传输就解决了。第二个是连续跑几小时后死机，用 FreeRTOS 的栈水位发现某个任务只剩 8 个字，把栈从 256 加到 512 后稳定跑过 24 小时。
>
> 最后指标是按键响应小于 50ms，屏幕 10 帧每秒，温度精度 ±0.5℃，连续运行 24 小时无复位。

::: note 为什么"难点"这一段最值钱
面试官听过太多"我用过 STM32、会 I2C/SPI/ADC"。这些是**教程内容**，谁都能说。

但"单独正常、一起异常 → 怀疑并发 → 逻辑分析仪看到传输被打断 → 加锁"是一条**完整的排查链**，它证明你：

1. 能观察现象并归纳规律；
2. 会用工具（逻辑分析仪、栈水位）；
3. 知道问题的**本质**（共享资源需要互斥），而不是背答案。

**准备 2 个这样的故事，比背 50 道八股有用。**
:::

## 2. C 语言：这 6 个必考

### 2.1 volatile

示例作答是一个完整的模块文件，直接放进 `App/Src/` 就能编译：

**文件：`App/Src/app_rx.c`**

```c
/* 示例作答：中断置标志、主循环轮询（volatile 的典型场景） */
#include "main.h"
#include "usart.h"

static volatile uint8_t g_rx_done = 0;   /* 每次都从内存真读，不许优化进寄存器 */
static uint8_t g_frame[16];

/* 串口接收完成回调：CubeMX 的 USART1_IRQHandler 会进来 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART1) {
        g_rx_done = 1;
    }
}

/* 启动一次中断接收；在 App_Init() 里调用 */
void App_RxStart(void)
{
    HAL_UART_Receive_IT(&huart1, g_frame, (uint16_t)sizeof(g_frame));
}

/* 主循环每圈调用；不加 volatile，-O2 下可能被缓存成死循环 */
void App_RxPoll(void)
{
    if (g_rx_done != 0U) {
        g_rx_done = 0;
        /* 这里解析 g_frame，示意 */
    }
}
```

在项目里，`App_RxStart()` 由 `App_Init()` 调用一次，`App_RxPoll()` 由 `App_Loop()` 每圈调用。

**为什么加 volatile**：编译器看不到"中断会改这个变量"，在 `-O2` 下它会把 `g_rx_done` 读进寄存器，然后认为循环条件永远不变，现象是"串口明明收了数据，程序就是不处理"。**为什么不用别的**：有人用 `__IO`（`volatile` 的宏别名）或内存屏障 `__DMB()`，前者只是写法不同，后者管的是访存顺序、不管"每次重新读"，不能替代。**哪些没写**：`USART1_IRQHandler` 和 NVIC 使能在 CubeMX 生成的 `stm32f1xx_it.c`/`usart.c` 里，`App_RxStart()` 由 `App_Init()` 调用。

**作用**：告诉编译器"这个变量可能被程序之外的因素改变"，**每次都从内存重新读**，不许优化到寄存器里。

**三个必用场景**：
1. 中断和主循环共享的变量；
2. 硬件寄存器（`*(volatile uint32_t *)0x40021000`）；
3. DMA 写入的缓冲区。

**它不是**：原子操作、内存屏障、线程安全。`volatile` 不能替代互斥量。

::: warn 面试陷阱：volatile 能保证原子性吗
**不能。** `x++` 是"读—改—写"三步，中间可能被中断打断；对 64 位变量或结构体更是必然出问题。`volatile` 只影响编译器优不优化，不影响 CPU 执行时会不会被打断。

原子性要靠**关中断 / 临界区 / 原子指令（LDREX/STREX）**。这是高频追问。
:::

### 2.2 static

| 用法 | 含义 |
| --- | --- |
| 函数内的 `static` 变量 | 生命周期变成整个程序，**只初始化一次**，函数退出不销毁 |
| 文件作用域的 `static` 函数/变量 | **只在本文件可见**，相当于 C 的"私有" |

工程里大量用第二种做封装：`bsp_oled.c` 里的内部函数全加 `static`，头文件只暴露 3 个 API。

### 2.3 const

- `const char *p`：指向的内容不能改，指针能改。
- `char * const p`：指针不能改，内容能改。
- `const char * const p`：都不能改。

口诀：**const 在 `*` 左边修饰内容，在右边修饰指针**。

### 2.4 大小端

- **小端**（STM32、x86）：低字节放低地址。`0x12345678` 在内存里是 `78 56 34 12`。
- **大端**（部分网络协议、51）：高字节放低地址。

判断方法（完整可编译的工具模块）：

**文件：`App/Src/app_util.c`**

```c
/* 示例作答：判断当前 CPU 的字节序，返回 1 = 小端 */
#include <stdint.h>

int App_IsLittleEndian(void)
{
    uint16_t x = 0x0001;          /* 存进去：低字节 0x01、高字节 0x00 */
    return *(uint8_t *)&x == 1;   /* 低地址若是 1 → 小端；是 0 → 大端 */
}
```

**为什么用 `uint16_t` 不用 `int`**：类型宽度固定，不受平台影响；`int` 在 16 位单片机上也是 2 字节，但面试答固定宽度更稳。**为什么不用 `union`**：`union { uint16_t v; uint8_t b[2]; }` 也能判，但取地址强转更短，且不依赖编译器对 union 的布局（标准保证，但读起来更绕）。**哪些没写**：不用 `<endian.h>`（那是 Linux 的东西），STM32 是 ARM Cortex-M，固定小端，这个函数主要是面试要你能说清"低地址放低字节"。

**通信协议里必须约定字节序**。你的串口帧如果发 `uint16_t` 直接 `memcpy`，对端是大端设备就会读反。s18 的采样帧就是手动拆成高字节在前，两端约定好即可。

### 2.5 内存分区

| 区 | 放什么 | 生命周期 | 大小 |
| --- | --- | --- | --- |
| **代码区 .text** | 机器码、常量 | 整个运行期 | Flash |
| **已初始化全局 .data** | `int g = 5;` | 整个运行期 | RAM，启动时从 Flash 拷贝 |
| **未初始化全局 .bss** | `int g;` | 整个运行期，启动清零 | RAM |
| **堆 heap** | `malloc` | 手动释放 | RAM，向上增长 |
| **栈 stack** | 局部变量、返回地址 | 函数调用期 | RAM，向下增长 |

::: note 嵌入式为什么尽量不用 malloc
1. **碎片**：反复申请/释放不同大小，堆里会留下无法利用的碎片，跑几天就分配失败。
2. **不确定性**：分配时间不固定，硬实时系统不能接受。
3. **失败处理**：嵌入式没有"内存不足弹窗"，`malloc` 返回 NULL 必须处理，否则空指针崩溃。

工程做法：**静态分配**（全局数组、内存池），或者用 FreeRTOS 的 `heap_4`（带碎片合并，仍不推荐频繁分配）。面试问"为什么不用 malloc"，答这三条就够。
:::

### 2.6 位操作（必写）

**文件：`App/Src/app_bit.c`**

```c
/* 示例作答：位操作的四个基本动作，纯函数，方便在 PC 上单测 */
#include <stdint.h>

#define BIT(n)        (1U << (n))   /* 1U 保证不触发有符号移位，n 取 0~31 */

uint32_t App_BitSet(uint32_t reg, uint8_t n)
{
    return reg | BIT(n);            /* 置位：第 n 位变 1 */
}

uint32_t App_BitClear(uint32_t reg, uint8_t n)
{
    return reg & ~BIT(n);           /* 清零：第 n 位变 0 */
}

uint32_t App_BitToggle(uint32_t reg, uint8_t n)
{
    return reg ^ BIT(n);            /* 翻转 */
}

uint32_t App_BitField(uint32_t reg, uint32_t val)
{
    /* 把 4~5 位改成 val 的低 2 位：先清零再或，才是"替换" */
    return (reg & ~(0x3U << 4)) | ((val & 0x3U) << 4);
}
```

真实寄存器写法是 `*(volatile uint32_t *)0x4001100C = App_BitSet(...)`。

**为什么用 `1U` 而不是 `1`**：`1 << 31` 在 32 位 `int` 上是未定义行为（符号位），加 `U` 变成无符号移位。**为什么"改连续位"要先清零再或**：直接 `| (val << 4)` 只能把位变 1，清不掉原来的 1；先 `& ~(mask)` 再或才是"替换"。**哪些没写**：真实使用必须通过 `volatile` 指针写寄存器，否则编译器会把多次读写合并；寄存器头文件里 ST 已经写好 `BSRR`、`BRR` 这类原子置位/清零寄存器，能一次写完成，比读-改-写更安全。

面试常考"用位操作实现两个数交换""统计二进制里 1 的个数""判断是不是 2 的幂"。

## 3. 单片机原理：三个必考流程

### 3.1 上电到 main 发生了什么

1. 复位，CPU 从 **0x08000000** 读**初始 MSP**（栈顶地址），从 **0x08000004** 读**复位向量**（Reset_Handler 地址）。
2. `Reset_Handler` 调用 `SystemInit()`：配时钟（HSE→PLL→72MHz）。
3. 把 `.data` 段从 Flash 拷贝到 RAM，把 `.bss` 段清零。
4. 调用 `__libc_init_array()`（C++ 全局构造、`__attribute__((constructor))`）。
5. 进入 `main()`。

::: note 为什么先设 MSP 再跳
因为 C 函数一调用就要用栈。如果 MSP 还是复位默认值（可能是 0 或随机），第一条 `push` 就会写飞。

所以 Cortex-M 的向量表第一项**固定是栈顶地址**，硬件在取复位向量前自动把它装进 MSP。这是硬件帮你做的第一件事。
:::

### 3.2 中断响应流程

1. 外设置中断标志，NVIC 判断优先级。
2. **硬件自动压栈 8 个寄存器**：R0-R3、R12、LR、PC、xPSR（保存现场）。
3. 取中断向量，跳进 ISR。
4. 执行 ISR，**清中断标志**（很多 bug 就是忘了清，导致反复进中断）。
5. 硬件自动出栈，回到被打断的地方。

进阶考点：
- **尾链（Tail-chaining）**：一个中断刚处理完，另一个挂起的中断直接进入，不做出栈再压栈，省 12 个周期。
- **迟到（Late arrival）**：压栈期间来了更高优先级中断，直接改跳更高优先级，不重复压栈。

### 3.3 HardFault 怎么查

**文件：`Core/Src/stm32f1xx_it.c`**

```c
/* 示例作答：覆盖启动文件里的弱定义 HardFault_Handler，并打印出错现场 */
#include "main.h"
#include "stm32f1xx_it.h"

void NMI_Handler(void)
{
    while (1) { }
}

void SysTick_Handler(void)
{
    HAL_IncTick();
}

/* 汇编只做一件事：判断出错时用的是 MSP 还是 PSP，把栈指针当参数传给 C */
void HardFault_Handler(void)
{
    __asm volatile (
        "tst lr, #4        \n"   /* EXC_RETURN 第 2 位：0 用 MSP，1 用 PSP */
        "ite eq            \n"
        "mrseq r0, msp     \n"   /* 主栈：把栈指针当第一个参数传下去 */
        "mrsne r0, psp     \n"   /* 线程栈（RTOS 任务里出错走这里） */
        "b hardfault_report\n"   /* 尾调用，不压栈、不返回 */
    );
}

/* 硬件压栈顺序：R0,R1,R2,R3,R12,LR,PC,xPSR → sp[5]=LR, sp[6]=PC */
void hardfault_report(uint32_t *sp)
{
    volatile uint32_t pc = sp[6];   /* 出错时的 PC */
    volatile uint32_t lr = sp[5];
    (void)pc;
    (void)lr;
    while (1) { }   /* 在这里打断点，看 pc 落在哪个函数 */
}
```

**为什么先用汇编写**：C 函数一进门就可能压栈，而此刻栈指针本身可能已经坏了；更关键的是硬件不告诉你出错时用的是 MSP 还是 PSP，只能读 `LR` 的 `EXC_RETURN` 判断。**为什么不用 `__get_MSP()` 直接读**：那只能拿到主栈，RTOS 任务里出错（PSP）就取错了现场，PC 自然是错的。**哪些没写**：8 个寄存器的压栈是 Cortex-M 硬件自动做的，不用你保存；`stm32f1xx_it.c` 原本就有 `HardFault_Handler` 的空实现，直接用上面整个文件替换即可，别在别处重复定义。

**排查思路**：拿到 PC，在 `.map` 文件或反汇编里查这个地址属于哪个函数，基本就锁定了。

常见原因：空指针、数组越界、栈溢出、函数指针没初始化、中断里调了禁止的 API。

## 4. 通信与外设：一张对比表打天下

| | UART | I2C | SPI |
| --- | --- | --- | --- |
| 线数 | 2（TX/RX） | 2（SCL/SDA） | 3+N（+CS） |
| 同步方式 | 异步（靠波特率） | 同步 | 同步 |
| 双工 | 全双工 | 半双工 | 全双工 |
| 速度 | ~几 Mbps | 100k~1M | 几 M~几十 M |
| 多设备 | 点对点 | 地址寻址 | 片选 |
| 电平 | 推挽 | **开漏 + 上拉** | 推挽 |
| 应答 | 无（可加校验） | 每字节 ACK | 无 |

必答的追问：

- **I2C 为什么开漏**：多设备线与，避免推挽冲突短路；上拉提供高电平。
- **SPI 四种模式**：CPOL 定空闲电平，CPHA 定第几个沿采样；数据在采样沿对侧变化。
- **UART 波特率误差**：一帧 10 位，累计误差不能超过半个位宽，容忍约 2%~3%。
- **DMA 有什么用**：外设和内存之间独立搬运，不占 CPU；配置注意地址递增和循环模式。
- **PWM 频率与分辨率**：`f = 72M/((PSC+1)(ARR+1))`，两者乘积受时钟限制，不可兼得。

## 5. RTOS：三个必答

1. **任务切换做了什么**：保存当前任务的寄存器到它的栈（PendSV 异常里完成），从下一个任务的栈恢复寄存器，更新 PSP。
2. **优先级反转是什么**：低优先级任务持有锁，高优先级任务等锁，中优先级任务抢占低优先级 → 高优先级被中优先级间接卡住。解法是**优先级继承**（互斥量）。
3. **栈溢出怎么发现**：FreeRTOS 在栈尾填魔数 `0xA5`，切换时检查；或 `uxTaskGetStackHighWaterMark` 看历史最小剩余。现象是随机 HardFault、变量被莫名改写。

## 6. 不会的问题怎么接

面试一定有不会的。**硬编比不会更致命**。

三种接法：

1. **承认 + 迁移**："这个我没用过。但如果它和 XX 类似，我猜是……我的依据是……"
2. **降维**："具体型号的寄存器我不记得，但这类外设的通用流程是：使能时钟 → 配引脚 → 配参数 → 开中断 → 启动。"
3. **反问确认**："您问的是硬件层面的实现，还是使用层面的配置？"——把问题变清晰，也给自己争取思考时间。

::: warn 三个减分动作
- **不懂装懂**：编一个听起来合理的答案，被追问两层就露馅。
- **沉默超过 10 秒**：可以先说"我想一下"，然后说出思考过程。
- **把话题扯到不相关的地方**：答不上来就承认，别绕。
:::

## 7. 模拟面试（先自己答，再看要点）

::: exercise 练习 1
`volatile` 的作用是什么？`volatile` 能保证多线程安全吗？
::: answer
**作用**：禁止编译器把变量缓存到寄存器，每次访问都从内存读/写。用于中断共享变量、硬件寄存器、DMA 缓冲区。

**不能保证线程安全**。它只保证"可见性"（每次都真读内存），不保证"原子性"。`x++` 是读-改-写三步，仍可能被打断。多任务共享数据要用临界区、互斥量或原子指令。
:::
:::

::: exercise 练习 2
I2C 为什么必须用开漏输出？如果改成推挽会怎样？
::: answer
I2C 是多设备共享总线。开漏输出只能"拉低"或"放手"，高电平由上拉电阻提供，所以多个设备同时驱动时是**线与**——最坏结果都是低电平，安全。

改成推挽后，设备会主动输出高（接 3.3V）。当 A 输出高、B 输出低时，**3.3V 和 GND 通过两个导通的 MOS 管直接短路**，电流可达安培级，烧毁芯片。

所以开漏 + 外部上拉是 I2C 的**电气前提**，不是可选项。
:::
:::

::: exercise 练习 3
一个 12 位 ADC、参考 3.3V，读到 1024，电压是多少？这个精度能测 1mV 的变化吗？
::: answer
$$1024 / 4096 \times 3.3 = 0.825V$$

1 LSB = $3.3/4096 \approx 0.806mV$。

**能分辨 1mV，但不准**。因为 1 LSB 是 0.806mV，1mV 的变化大约对应 1.24 个码值，会出现"跳 1 或跳 2"的量化噪声。再叠加 ADC 本身的 ±1~2 LSB 误差和参考电压误差，**单次读数无法可靠分辨 1mV**。

要测 1mV 需要：过采样 + 平均（分辨率换精度）、更高位 ADC、或校准参考电压。
:::
:::

::: exercise 练习 4
FreeRTOS 里，一个高优先级任务一直 `while(1)` 不让出 CPU，会发生什么？
::: answer
**低优先级任务永远得不到执行（饿死）**，包括空闲任务。

后果：
1. 空闲任务没机会回收已删除任务的内存（`vTaskDelete` 后资源泄漏）。
2. 低优先级的显示、通信、看门狗喂狗全部停摆 → 看门狗复位。
3. 同优先级的其他任务也拿不到时间片。

**正确做法**：每个任务必须有阻塞点（`vTaskDelay`、等队列、等信号量）。真要跑满 CPU 的计算任务，应把优先级设为最低，或定期 `taskYIELD()`。
:::
:::

::: exercise 练习 5
你的串口收到一堆乱码，怎么排查？
::: answer
按"从物理到软件"的顺序：

1. **波特率是否一致**（最常见）。用示波器量一位宽度：115200 应为 8.68μs。偏一倍就是时钟/分频算错。
2. **TX/RX 是否交叉**：板子 TX 接模块 RX。
3. **是否共地**：不共地会时好时坏。
4. **电平是否匹配**：3.3V TTL 与 RS232/5V 不能直连。
5. **时钟源**：USART1 是 72MHz，USART2 是 36MHz，配错就差一倍。
6. **数据位/校验/停止位**是否和对方一致（8-N-1）。

先量波形，比盯着乱码猜快得多。
:::
:::

## 8. 面试最后：反问什么

**不要说"没有了"。** 反问是展示你思考深度的机会：

:::

## 9. 本课小结

- 项目讲述用**背景→方案→难点→结果**四段式，**难点**那段最值钱。
- C 语言六件套：`volatile`（可见性非原子）、`static`、`const`、**大小端**、内存五区、位操作。
- 三个流程：**上电到 main**（取 MSP/向量 → SystemInit → 拷 .data → 清 .bss → main）、**中断响应**（硬件压 8 个寄存器）、**HardFault 查 PC**。
- 通信对比表要能脱口而出，尤其是 **I2C 开漏** 和 **SPI 四模式**。
- RTOS 三问：任务切换（PendSV 保存/恢复）、优先级反转（优先级继承）、栈溢出（水位/魔数）。
- 不会就承认 + 迁移 + 降维，别硬编。
- 面试最后一定要反问。
